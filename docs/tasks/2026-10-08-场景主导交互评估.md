## 评估结论与源码依据

工程量适合推进，属于中等规模的界面与交互映射改造。现有 TypeScript/DOM/Vite/Tauri、31张本地图片、剧情和存档可复用。完整改造纳入现有87个剧情节点；样板只是实施顺序，不代表其余场景不再纳入。

当前问题主要在呈现架构：`index.html`把`.scenery`与`#app`分成相邻容器，`styles.css`使用46%/54%双栏；`main.ts`的`updateScenery()`直接更换src，`renderStory()`重新构建正文与全部按钮，未等待目标图片解码，也未区分移动、调查与对话时序。`choiceAppearance()`按中文正则分样式，不能作为动作方位依据。

`SceneId`同时代表地点、调查、对话和结果；`reception→hallPortrait`是同场调查，`truthHub→kitchenQuestion`是同场对话，不应每次都演成离开/进入房间。`getScene()`统一筛选可用动作，`recordChoice()`与`commitRecords()`已有记录和保存边界，可继续作为唯一行为入口。`Scene.paragraphs`没有说话人元数据，角色气泡和逐句演出需另做呈现标注，不能猜测人物身份。

仅扩大图片、把同样的全部按钮放到底部，不足以满足用户目标。必须让门、人物、物件和方向成为实际操作入口。

## 推荐交互

已确认需求是场景为主体、文字与行动融入、换景后自然浮现、后续可加自然过场。以下形式、时间与接口均为建议，尚未实现。

| 内容 | 推荐呈现 | 约束 |
| --- | --- | --- |
| 背景 | 持续场景舞台，文字和行动属于其前景 | 不为铺满窄屏裁掉门/线索；保留完整图观察 |
| 门/楼梯/通路 | 目标附近轻量标记，聚焦或触摸显示行动文字 | 画中有门不等于可通行，只映射getScene返回的choice |
| 前台人物 | 点击人物，打开办理/对话的上下文面板 | 只用玩家已知称呼，多个追问收进人物组 |
| 肖像/登记簿/水杯 | 物件入口，进入特写或原地调查 | 后续选择在观察后出现，不做隐蔽像素搜索 |
| 画面外目的地 | 边缘有名方向出口，如水井/林路 | 不挂到无关物件，不增加无条件返回 |
| 旁白与决定 | 场景安全区域短段落、上下文选项 | 完整文字可回看，长文可展开，不强制逐字等待或每句点击 |
| 系统功能 | 小型常驻入口，物品/存档/记录展开覆盖层 | 系统层重绘不写剧情；归档和回溯规则保留 |
| 谜题与结局 | 局部操作层/可读结局层，背景保留 | 40端点、零交叉、实时保存和重玩入口保留 |

推荐顺序：**接受选择并保存→准备目标图→场景转化→旁白出现→行动浮现并可操作**。淡入建议从300–500ms试起；用短促显现衔接文字与行动，不通过固定计时猜玩家阅读速度。长对话由玩家推进或显示全文；提供立即显示与减少动画，显示过程不自动执行下一步剧情。

空间移动使用淡入或轻微镜头变化；同场对话保留环境；调查进入特写；返回恢复环境与目标焦点。同图下林路步数、物品或台词变化仍需更新，不能只按图片src判断有无有效内容。

### 首个可玩样板

1. 门前：门上“进入旅馆”，水井和林路为方向出口。
2. 点击门执行原`enter`一次并保存；大厅图就绪后出现旁白和问答，再显示人物、登记簿、画像入口。
3. 点击人物打开办理动作；点击登记簿进入原调查；点击画框执行`look-hall-portrait`并进入特写。
4. 观察后出现“回到柜台前”，执行原`back-reception`；恢复大厅、焦点回画框，不重演推门。既有文案中的新增线索不能因此丢失。

## 技术接口与风险边界

模块名为建议，尚未创建。首期预计不改`src/game/types.ts`、`state.ts`、`engine.ts`、`records.ts`和存档格式，确需修改时再说明理由并指定负责人。

- 新`src/ui/sceneStage.ts`：持续舞台、双图缓冲、解码、前景显现；建议`present(frame, {reason, signal})`、`revealNow()`、`cancel()`。
- 新`src/ui/scenePresentation.ts`：按`sceneId+choiceId`描述类型、对象、动作组、归一化图坐标与转换；运行时与`getScene().choices`取交集，不在UI复写剧情条件。未映射的可用动作始终有明确可达入口，推广完成前检查零遗漏。
- 图源仍集中`src/ui/sceneArt.ts`；锚点按图片实际显示矩形计算，处理contain留白、缩放、resize、变体构图。窄屏允许场景内托盘重排，重要行动支持键盘和触摸，不能只靠悬停。
- 点击时同步校验/锁定/执行记录/提交保存，再异步显示。动画不领取物品、不写日记；中断显示不回滚选择，刷新直接恢复已保存目标节点。
- `viewEpoch`/`AbortController`取消旧图片解码、计时与回调；标题、菜单、读档、回溯、重开使旧视图失效。仅`game !== snapshot`不足以处理打开菜单但状态不变的情况。绳阵使用旅程ID、场景和弹窗会话标记，避免合法移动使初始状态引用变化而被误拦截。
- 不全量预加载31图，只准备当前、目标或少量可确定相邻图。缺图、解码拒绝和超时能退化到明确提示与文字，不能永久锁住行动或拿旧房间图冒充新地点。
- 未来独立`transitionAdapter`按来源/目标空间与动作指定镜头，可取消/跳过、无素材退回淡入。真正开门穿行、楼梯移动、分层或视频需要额外素材，单独估量，不纳入本轮制作。

## 分期与工程量

假设熟悉工程、复用31图、保留剧情规则与存档、沿用DOM并包含网页验证；以下是开发工作量估算，**不是自动执行耗时或交付日期承诺**。

| 阶段 | 交付 | 粗估工作量 | 完成边界 |
| --- | --- | --- | --- |
| 1. 可玩样板 | 门前/大厅/登记簿/肖像/返回；舞台、真实对象入口、显现顺序、手机和中断 | 2–4个开发工作日 | 验证体验方向，其余节点保有可达入口；不宣称全游戏完成 |
| 2. 全内容推广 | 全87节点分类和行动覆盖，其余空间/物件/人物/出口，菜单、谜题、结局 | 额外4–8个开发工作日 | 正常探索以场景内入口组织，全部列表不是长期最终形态 |
| 3. 集成审计修正 | 取消/保存/故障回归、四结局、手机/键盘、图面遮挡、文档 | 额外2–3个开发工作日 | 验收全部达成才算首轮完整改造完成 |
| 后续演出 | 开门、楼梯、昼夜、人物等专门镜头/素材 | 按镜头单独评估 | 接入预留过场接口 |

总量粗估8–15个开发工作日。全部节点能在新舞台运行，比全部核心行动贴合场景容易，前者只是中间里程碑。最大浮动来自长对白整理、手机目标大小、图像变体位置与局部谜题连续性。先样板后推广可以先验证这些问题。

## 实施验收与验证计划

- 门、人物、画像和登记簿能从场景中操作；目标图就绪后文字行动显现，同场对话不重演换房。
- 所有当前可用choice有入口，锁定/未知信息不泄露，返回遵守规则，四结局仍可达。
- 连击、键盘重复与旧回调不重复推进、领取或记录。准备B图时打开菜单/读档C，晚到B不覆盖C。
- 过场中刷新恢复已保存目标；读档/回溯归档一次，跳过/重绘/系统功能不补写剧情。
- 缺图、decode拒绝、超时、零动画不永久锁定；保存失败及其他窗口冲突提示不被遮挡。
- 绳阵全部40端点可移动、零交叉完成，关闭重开保持布局，移动实时保存，领钥匙一次。
- 桌面/390px窄屏核查对象与标记、触摸目标、长文、多选项、焦点、Esc返回，关键物件不被裁掉/遮住，仍能查看完整图。隐藏阶段不聚焦不可见行动。
- 实施后运行`npm.cmd test`与`npm.cmd run build`；增加异步竞争、故障与动作覆盖的风险测试，独立来源保护玩家存档。需要桌面交付时再构建NSIS。
